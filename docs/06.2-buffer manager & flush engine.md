# Phase 6.2 — Buffer Manager & Flush Engine

## Goal

Implement the high-performance write buffering layer for TraceForge Storage.

The Buffer Manager decouples repositories from storage I/O by accumulating immutable storage records into deterministic batches before they are persisted through the Storage Driver.

This phase introduces batched writes, configurable flush policies, transaction orchestration, and failure isolation while preserving deterministic replay and append-only persistence.

# Responsibilities

## BufferManager

The Buffer Manager is responsible for temporarily holding immutable Storage Records in memory until a flush condition is satisfied.

Responsibilities:

- Accept Storage Records from repositories
- Preserve insertion order
- Support batched retrieval
- Maintain thread safety
- Never perform storage I/O
- Never perform transactions
- Never serialize records

Public API

```python
append(record)

append_many(records)

peek()

drain()

size()

is_empty()

clear()
```

---

## Batch

Represents an immutable collection of Storage Records.

Responsibilities:

- Hold records
- Preserve deterministic ordering
- Carry batch metadata

Fields

- batch_id
- created_at
- records
- record_count

Batch instances are immutable.

---

## FlushPolicy

Determines when buffered records should be flushed.

Flush policies contain no storage logic.

Built-in policies

### SizeFlushPolicy

Flush when

```
buffer_size >= max_records
```

---

### TimeFlushPolicy

Flush when

```
elapsed_time >= interval
```

---

### HybridFlushPolicy

Flush when either condition becomes true.

```
Size
OR
Time
```

This becomes the default policy.

---

## FlushEngine

Responsible for moving batches from memory into persistent storage.

Responsibilities

- Drain buffer
- Create Batch
- Begin transaction
- Write batch
- Commit
- Rollback on failure
- Preserve deterministic ordering

FlushEngine never owns storage records.

---

## TransactionManager

Coordinates transactional writes using the StorageDriver contract.

Responsibilities

- begin_transaction()
- commit()
- rollback()

Repositories never directly manage transactions.

# Design Principles

## Append-only

Buffered records are immutable.

Existing records are never modified.

---

## Deterministic Ordering

Records are flushed in the exact order they entered the buffer.

Batch ordering is preserved.

Replay must remain deterministic.

---

## Driver Independence

Buffer Manager communicates only with

- TransactionManager
- StorageDriver

No SQLite-specific logic exists in this phase.

---

## Failure Isolation

Storage failures never corrupt buffered records.

Failed batches remain recoverable.

Rollback restores transactional consistency.

---

## Thread Safety

Buffer operations are synchronized.

Concurrent producers are supported.

Flush operations remain deterministic.

---

## Separation of Responsibilities

BufferManager

- Memory management

FlushPolicy

- Flush decision making

FlushEngine

- Persistence orchestration

TransactionManager

- Transaction lifecycle

StorageDriver

- Physical persistence

# Constraints

The Buffer Manager

MUST

- preserve ordering
- be thread safe
- support concurrent producers
- support deterministic replay

MUST NOT

- write to storage
- own transactions
- serialize records
- mutate records

---

The Flush Engine

MUST

- flush complete batches
- rollback failed transactions
- preserve ordering

MUST NOT

- mutate records
- reorder batches

---

The Transaction Manager

MUST

- coordinate begin
- commit
- rollback

MUST NOT

- know repository internals

---
