# Phase 6.1 — Storage Architecture

## Goal

Design a production-grade persistence architecture that stores immutable execution artifacts generated by the Recording Engine while remaining:

- Deterministic
- Thread-safe
- Append-only
- Driver-independent
- High-performance
- Extensible

The Storage Engine is responsible for persistence only.

It does **not** perform querying, indexing, visualization, analytics, replay, or AI reasoning.

---

# Design Principles

## Immutable Persistence

Once an execution artifact is committed to storage, it must never be modified.

Supported operations:

- Append
- Read (future Query Engine)

Unsupported operations:

- Update
- Delete

Deletion is reserved exclusively for administrative retention policies and maintenance operations.

---

## Driver Independence

Repositories never depend on a concrete storage implementation.

Repositories never know:

- SQLite
- JSONL
- Memory storage
- Future storage backends

Repositories communicate exclusively through the Storage Driver abstraction.

---

## Deterministic Persistence

Persisting identical execution artifacts must always generate identical persistent representations.

Ordering is deterministic and preserved.

Persistence order:

1. RecordingSession
2. Activity
3. ExecutionGraph
4. ExecutionNode
5. Relationship
6. SessionSnapshot
7. RawEvent

---

## Aggregate Ownership

Repositories follow Aggregate Roots defined by the Domain Model.

Only two repositories exist:

- SessionRepository
- RawEventRepository

All execution artifacts except RawEvents belong to the Session aggregate.

---

## CQRS Separation

The Storage Engine is responsible only for the write side.

Responsibilities include:

- Persisting immutable execution artifacts
- Managing buffering
- Managing transactions
- Delegating persistence to storage drivers

Reading, searching, filtering, indexing, and analytics belong exclusively to the future Query Engine.

---

# Repository Layer

## SessionRepository

Owns persistence of the Session aggregate.

Responsible for appending:

- RecordingSession
- Activity
- ExecutionGraph
- ExecutionNode
- Relationship
- SessionSnapshot

Example API:

```python
append_session(session)

append_activity(activity)

append_graph(graph)

append_snapshot(snapshot)
```

The repository never exposes:

- update()
- delete()
- replace()

---

## RawEventRepository

Responsible only for persisting raw runtime events.

Example API:

```python
append_raw_events(events)
```

No additional responsibilities are permitted.

---

# Storage Records

Repositories convert immutable Domain Models into immutable Storage Records.

```
RecordingSession
        │
        ▼
SessionRecord
        │
        ▼
Storage Driver
```

Storage Records exist only inside the Storage layer.

The Domain layer must never import, reference, or depend upon Storage Records.

---

## Record Types

- SessionRecord
- ActivityRecord
- GraphRecord
- NodeRecord
- RelationshipRecord
- RawEventRecord
- SnapshotRecord

All Storage Records are immutable.

---

# Storage Driver

Every storage backend implements the same abstract interface.

```python
class StorageDriver(ABC):

    def begin_transaction(self):
        ...

    def commit(self):
        ...

    def rollback(self):
        ...

    def write_batch(self, records):
        ...

    def flush(self):
        ...

    def close(self):
        ...
```

Storage Drivers never receive Domain Models.

Storage Drivers receive only Storage Records.

---

# Append-Only Write Model

Supported operations:

- append_session()
- append_activity()
- append_graph()
- append_node()
- append_relationship()
- append_snapshot()
- append_raw_events()

Unsupported operations:

- update()
- delete()
- replace()

Execution history is immutable.

---

# Thread Safety

The Storage Engine must support concurrent recording safely.

Requirements:

- Repositories are thread-safe.
- Buffer Manager serializes writes.
- Storage Drivers are thread-safe.
- Multiple recording threads may append concurrently.
- Internal synchronization must rely on reentrant locks where shared mutable state exists.

---

# Transaction Ownership

Transaction management belongs exclusively to the Transaction Manager.

Repositories never begin or commit transactions.

Transaction lifecycle:

```
BEGIN
    ↓
Batch Writes
    ↓
COMMIT
```

On failure:

```
BEGIN
    ↓
Batch Writes
    ↓
ROLLBACK
```

Repositories remain transaction-agnostic.

---

# Failure Isolation

Storage failures must never terminate:

- Recorder
- Plugin SDK
- Runtime Plugin
- Instrumentation API
- Host Application

Storage failures are converted into Storage Events and propagated through the Execution Pipeline.

Recording continues whenever safely possible.

# Architectural Guarantees

The Storage Architecture guarantees:

- Immutable persistence
- Deterministic storage
- Append-only execution history
- Driver independence
- Repository isolation
- Aggregate ownership consistency
- Thread-safe persistence
- Transaction isolation
- Failure isolation
- Future compatibility with additional storage backends
- Clean separation between Write Model (Storage Engine) and Read Model (Query Engine)

---

# Out of Scope

The following capabilities are intentionally excluded from Phase 6.1:

- Query execution
- Search
- Filtering
- Dashboard APIs
- AI analysis
- Replay engine
- Index optimization
- Schema migrations
- Buffer management
- Flush policies
- Batch scheduling
- Recovery mechanisms

These capabilities are implemented in subsequent phases.
